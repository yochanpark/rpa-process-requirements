# 1. 업무 분해 방식

## 과제 단위로 자른다

RPA 요건정의의 첫 단계는 **"어디까지를 한 과제로 볼 것인가"** 를 정하는 것이다.
너무 크게 잡으면 요건서 안에서 분기가 폭발하고, 너무 잘게 자르면 과제 간 중복이 생긴다.

이 건에서는 **입력 경로가 갈리는 지점**을 기준으로 잘랐다.

SO/PO 등록은 업무 이름으로는 하나지만 실제로는 셋이었다.

| 패턴 | 흐름 |
|---|---|
| 1 — 직송·무상샘플 | 고객사 발주서 도착 → D365에 매출등록(SO) → 매칭하여 매입 발주서(PO) 발행 |
| 2 — 재고 | 발주수량 확정(Excel) → D365 로그인 → 매입 발주서(PO) 발행 |
| 3 — 재고·커미션 | 재고: 발주서 도착 → 매출등록(SO) / 커미션: 품목 리스트 등록 + 커미션율 입력 → 매출등록(SO) |

시작 트리거(발주서 도착 / 수량 확정)와 등록 대상(SO 먼저 / PO 먼저)이 달라
하나의 시나리오로 합칠 수 없었다.

## 추출·가공형은 성격이 다르다

SalesReport 메일링, Inventory 가공, Sales Report 가공은 **입력이 아니라 출력** 쪽이다.

SalesReport 메일링의 경우:

```
① D365에서 세일즈리포트 출력
② 해당월 실적 PV를 팀별·제품군별 금액과 환차손으로 정리
③ 표로 만들어 메일 발송
```

여기에 요청이 하나 더 붙었다 — **별도 Excel에 작성된 계획 수치와 D365 실적을 자동 비교**.
비교 기준은 팀 / BU / 판매기준 / 제품군 네 축이다.

입력형은 "화면에 무엇을 넣는가", 출력형은 "어떤 기준으로 집계하는가"가 요건의 핵심이라
요건서 구성 자체를 다르게 잡았다.

## 화면 녹화로 프로세스를 복원한다

담당자 설명만으로는 실제 클릭 순서와 필수 입력값을 알 수 없다.
**업무 수행 화면을 녹화받아 프레임을 캡처하고, 스크린샷에 번호를 붙여 요건서에 넣었다.**

과제당 8~19장이 나왔다. 이 방식의 이점은 두 가지다.

- 담당자가 말로 빠뜨린 단계(팝업 확인, 탭 전환)가 화면에는 남는다
- 개발자가 요건서만 보고도 **화면 요소를 특정**할 수 있다

회계전표입력처럼 입력 항목이 많은 업무(TEAM, BU, VAT 종류, DUE DATE, 거래처 등)는
특히 녹화 없이는 필드 목록조차 확정할 수 없었다.
